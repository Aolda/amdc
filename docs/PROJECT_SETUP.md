## 결정 근거

### 확인된 사실

- 활성 저장소는 `https://github.com/Aolda/amdc`입니다. GitHub 기본 브랜치는 `main`이지만 최근 병합된 구현 PR #3, #5, #6은 `develop`을 대상으로 하므로 현재 팀 통합 경로는 `develop`입니다.
- 여러 기여자가 GitHub 이슈와 PR을 통해 작업을 인계했습니다. 이슈 #1과 병합된 PR #3, #5, #6은 GitHub가 기존 실행 경로임을 보여 줍니다.
- `docs/prd/current/README.md`와 번호가 매겨진 PRD가 P0 제품 계약을 소유합니다.
- 저장소에는 Discord 어댑터, LangChain 진단 골격, YAML 도구 런타임, 설정된 HTTP 상태 확인 어댑터가 있지만 자동화된 테스트 명령이나 검증된 P0 핵심 수직 흐름은 없습니다.
- PRD 04는 현재 코드만 대상으로 한 테스트 골격이 존재하고 `npm test`가 이를 실행할 때까지 정본 P0 `Delivery Status`를 `not_started`로 유지합니다. 기존 초안과 충돌하는 코드는 시제품 또는 전환 증거이며 검증된 P0 전달 결과가 아닙니다.
- AMDC는 인증 정보, 배포 과정에서 주입된 자격 증명, 외부 운영 원천과 선택적 운영 환경 접근을 처리합니다. P0는 읽기 전용으로 유지되지만 실패 시 비밀정보가 노출되거나 잘못된 운영 결과가 생성될 수 있습니다.
- GitHub 이슈 #7은 별도의 리포트 에이전트 및 영속화된 Discord 전달 기능입니다. `OstenHun`에게 할당되며, 안정적인 도구 호출 참조를 전달하는 제한된 순서 보존 진단 출력 포트에 대해서만 이슈 #4에 GitHub 네이티브 의존성이 있습니다. 이슈 #4는 `worud8457`에게 할당되며, Discord 봇 접점은 #4의 산출물이 아니라 #7의 통합 검토 경계로 남습니다.

### 가정

- 팀이 이미 사용 중이므로 GitHub 이슈와 PR을 단일 실행 추적기로 유지합니다. 두 번째 관리 평면, Jira 또는 로컬 상태 원장은 중복 상태를 만듭니다.
- 팀이 다른 승격 계약을 기록할 때까지 구현 PR은 계속 `develop`을 대상으로 합니다. `main`으로의 승격은 별도 결정이며 브랜치 이름만으로 배포 또는 검증 상태를 추론할 수 없습니다.
- 이슈 담당자가 작업 항목 담당자입니다. `Verify` 전에 최소 한 명의 비작성자 검토자를 요청하며, 계약 또는 고위험 경계 변경에는 영향을 받는 계약이나 시스템의 담당 검토자도 필요합니다.

### 미결정 질문

- #4/#7 인계 외 담당자의 안정적인 별칭은 미결정입니다. #7 작업 항목 담당자는 GitHub 담당자 `OstenHun`이며, 구체적인 비작성자 Discord/Diagnostic 통합 검토자는 `worud8457`이고 `Verify` 전에 구현 PR에서 요청해야 합니다.
- `develop`과 GitHub 기본 `main` 사이의 정확한 승격 규칙은 미결정입니다. 어느 이름에서도 환경이나 릴리스 상태를 추론하지 않습니다.
- PRD 06의 리포트 인계가 현재 기준입니다. 진단 정적/YAML 정렬은 미결정이며, 별도 결정 전까지 PRD 00/02의 정적 레지스트리가 규범입니다.
- 실제 어댑터가 구현 범위에 들어가기 전에 PRD 05에는 AMDB 원천 담당자가 제공하는 정본 Prometheus, Loki 및 Backend 매핑이 여전히 필요합니다.

## 프로젝트 결과

- 문제 또는 기회: AMDB 조사가 느리고 담당자 의존적이지만 에이전트에 직접 운영 권한을 주면 허용할 수 없는 비밀정보·환경·오진 위험이 생깁니다.
- 다음 최소 결과: 실제 자격 증명 없이 가짜 구현 기반 `backend_5xx_increase` 핵심 실행이 정제된 증거와 스키마에 맞는 리포트를 하나의 조정된 런타임 계약을 통해 생성합니다.
- 성공 근거: 현재 코드만 대상으로 한 자동화 테스트 명령, `npm run typecheck`, `npm run build`가 통과하고 필수 고정 데이터 결과와 실패 주입이 통과해야 합니다. 자격 증명이 포함된 프로세스 환경 값, 런타임 프롬프트 전문, 원시 제공자/원천 응답은 영속화하거나 반환하지 않습니다. 버전 관리되는 프롬프트 템플릿과 스키마가 승인한 `dev | prod` 환경 값은 허용합니다. 자동화 테스트 명령이 생기기 전까지 결과는 `verified`가 아닙니다.

## 운영 구조

### 작업 항목 의미

- Feature: 관찰 가능한 인수 증거가 있는 사용자 또는 프로젝트 결과
- Spike: 중요한 불확실성 하나를 해소하는 시간 제한 조사
- Task: 알려진 구현 또는 유지보수 작업
- Bug: 계약된 동작과 관찰된 동작 사이의 차이

가능하면 일치하는 `type:*` 레이블을 사용합니다. 레이블이 없다고 새 추적기를 만들지 말고 이슈 제목과 본문에 유형을 적습니다.

### 작업 흐름 및 진행 중 작업 제한

| 상태 | 진입 규칙 | 종료 규칙 |
|---|---|---|
| Backlog | 구체적인 문제가 있는 이슈가 존재 | PAAR, 담당자, 검토 역할 및 의존성 검토 완료 |
| Ready | Problem, 대안, 제한된 Action, 측정 가능한 Result, GitHub 담당자와 필수 검토 역할이 명시됨 | 담당자가 브랜치 또는 초안 PR 시작 |
| In Progress | 한 담당자가 항목을 변경하거나 조사 중 | 인수 증거가 검토 준비됨 |
| Verify | PR을 검토할 수 있고 정확한 검증 증거가 첨부됨 | 필수 검토와 점검 통과 |
| Done | PR이 병합되고 이슈가 닫힘 | 새롭고 상반된 증거가 있을 때만 재개방 |

- 기본 진행 중 작업 제한은 담당자당 `In Progress` 항목 하나입니다. 차단된 항목은 추가 항목 하나를 허용할 수 있지만 차단 요인과 다음 차단 해제 조건을 기록해야 합니다.
- 가능하면 `blocked`를 사용하고, 누락된 입력 또는 실패한 점검, 담당자와 다음 검토 조건을 항상 기록합니다.
- 최소 두 개의 독립적인 작업 항목이 같은 결과나 릴리스 경계를 필요로 하기 전에는 주기, 스프린트, 마일스톤 또는 상위 이슈를 추가하지 않습니다.

### 브랜치 및 검토 흐름

1. 깨끗하거나 의도적으로 변경된 작업 트리임을 확인한 뒤 현재 `develop`에서 시작합니다.
2. 정해진 `feature/<alias>/<slug>` 패턴 또는 이에 준하는 `fix/` 접두사를 따라 작업 항목마다 단기 브랜치를 하나 만듭니다. 기존 원격 브랜치가 접두사를 차지하면 해당 참조 아래에 중첩하지 말고 `feature/<alias>-<slug>` 같은 형제 이름을 사용합니다.
3. `develop`으로 PR을 열고 소유 이슈 하나와 영향을 받는 모든 PRD/스키마를 연결합니다.
4. 분리하면 검증할 수 없는 중간 상태가 될 때 계약, 스키마, 구현 및 검증 변경을 같은 PR에 유지합니다.
5. 비작성자 검토자가 인수 증거를 확인합니다. 고위험 경계에는 영향을 받는 계약/시스템 소유권 검토도 추가로 필요합니다.
6. 아래 완료 기준을 충족한 뒤에만 병합하고 이슈를 닫습니다.

### 준비 기준

- Problem이 사용자, 병목, 실패 조건 또는 위험을 식별합니다.
- Analysis가 제안 경로를 최소 하나의 신뢰할 수 있는 대안과 비교하고 각 실패 모드를 명시합니다.
- Action이 파일/인터페이스, 명시적 비목표, 의존성과 롤백을 정합니다.
- Result에 측정 가능한 임계값과 재현 가능한 검증 환경이 있습니다.
- GitHub 담당자, 필수 검토 역할, 영향받는 계약과 위험 등급을 명시합니다. 구체적인 비작성자 검토자를 `Verify` 전에 요청합니다.
- 실제 자격 증명, 운영 환경 호출, 변경 작업 또는 파괴적 데이터 작업에는 별도 명시적 승인과 롤백/복구 계획이 필요합니다.

### 완료 기준

- 인수 기준을 충족하고 구체적인 변경 내용 및 증거에 연결합니다.
- 정확한 검증 명령, 환경, 결과와 미검증 공백을 PR에 기록합니다. 간이 점검을 자동화 테스트 모음으로 보고하지 않습니다.
- 계약/스키마 변경은 소유 PRD와 검증기에 함께 적용합니다.
- 관련 범위에서 시간 초과, 부분 실패, 권한 거부, 비밀정보 노출, 스키마 불일치와 롤백 실패 경로를 다룹니다.
- 자격 증명이나 비밀정보 값, 원시 인증 출력, 개인 키, 추적 중인 `.env` 할당, 런타임 프롬프트 전문, 원시 제공자/원천 응답이 코드, 문서, 로그, 고정 데이터 또는 리포트에 나타나지 않습니다. 버전 관리되는 프롬프트 템플릿과 스키마가 승인한 환경 값은 허용합니다.
- 작성자가 아닌 검토자가 승인하고 PR이 `develop`에 병합되며 소유 이슈가 닫히거나 명시적으로 대상이 재지정됩니다.

## 필수 산출물

- 중요 변경마다 `.github/ISSUE_TEMPLATE/work-item.md`를 사용하는 GitHub 이슈 하나
- 모든 병합마다 `.github/PULL_REQUEST_TEMPLATE.md`를 사용하는 PR 하나
- 계약 또는 스키마 변경: 소유 번호 PRD, 검증기와 테스트
- 실제 원천 작업: 검토된 PRD 05 원천 계약, 정제된 고정 데이터, 담당자, 검토일과 읽기 전용 개발 환경 간이 점검 승인
- 공통 영역의 되돌리기 비용이 큰 결정: 이슈와 소유 PRD에서 연결한 집중 결정 기록

## 생략한 절차

- 두 번째 추적기, 로컬 상태 원장, 스토리 포인트, 상시 스프린트 또는 영구 상위 이슈 계층을 만들지 않습니다.
- 이 단계에서는 Dev Atlas 사이트, 생성 대시보드 또는 중복 진행률을 만들지 않습니다. 경량 작업 흐름이 실제 PR 간 추적성을 반복해서 보존하지 못할 때만 재검토합니다.
- 안정적인 담당자 별칭과 경로 책임을 명시적으로 확인하기 전에는 `CODEOWNERS` 파일을 만들지 않습니다.
- 일상 검증의 일부로 운영 환경 간이 점검, 배포, 변경 작업 또는 자격 증명 검사를 수행하지 않습니다.

- Action(실행): PRD 06의 버전이 있는 호환 어댑터와 도구 없는 리포트 에이전트, 이어서 PRD 03의 결정적 조립, 원자적 영속화 및 영속화된 리포트 전용 Discord 접점을 구현합니다. 진단/YAML 내부를 재설계하거나 정적 런타임과 YAML 런타임 중 하나를 결정하지 않으며, 실제 어댑터나 Discord 재시도, 재전달, 전달 원장을 추가하지 않습니다. 상위 코드를 다시 작성하지 않고 접점을 롤백할 수 있도록 검증된 전환까지 임시 표시 계층을 유지합니다.
- Result(결과): PRD 04의 가짜 구현 기반 계약 매트릭스에서 다른 Run 참조 또는 추적 불가능한 산출물, 영속화 전 Discord 호출, 비밀정보 노출 및 애플리케이션 수준 Discord 재시도가 모두 0이어야 합니다. 정확한 테스트/빌드 명령, 호출 횟수 단언, 최종 DB 단언 및 제한된 접점 변경을 구현 PR에 첨부합니다.

현재 R0 문서 전용 PR은 이 인계를 준비할 뿐 이슈 #7을 구현하거나 닫지 않습니다. 패키지의 `Delivery Status`는 PRD 04의 진입 및 완료 조건을 충족할 때까지 `not_started`로 유지됩니다. 이 초기 설정 PR은 #7을 참조하지만 닫지 않는 명시적 전환 산출물입니다. 중요하지 않은 변경을 제외한 모든 변경에 이슈 하나를 요구하는 규칙은 이 설정이 병합된 뒤의 후속 작업 항목에 적용됩니다.
