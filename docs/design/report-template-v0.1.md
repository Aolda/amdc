## 설계 선택

**Problem**

독자가 조회 성공을 정상으로, 빈 결과를 복구로, 진단 코멘트를 원천 사실로 읽을 수 있다. 현재 MySQL 투영은 행 수·잘림만 남기므로 구체적 관측을 요구하는 템플릿을 프롬프트 변경만으로 채울 수 없다.

**Analyze**

현재 메타데이터만으로 모든 문구를 제한하면 즉시 재현하기 쉽지만 잠금 관계 같은 핵심 근거가 빠진다. 정제된 구조화 근거를 전제로 목표 출력을 설계하고 현재 가능한 표현을 병기하면 입력 공백이 드러나지만, 적용 전에 계약·검증 작업이 필요하다. 원시 결과 또는 자유형 코멘트를 사실로 복사하는 안은 근거 검증을 우회하므로 채택하지 않는다.

**Action**

두 번째 방식을 문서 설계로 선택한다. 사람용 7구획과 Discord 요약, 네 합성 사례, 입력·책임 표를 작성한다. 제품 코드·스키마·프롬프트·원천 호출은 범위 밖이다. 롤백은 이번 문서와 연결 문장만 되돌리는 것이다.

**Result**

고정 사례에서 근거 없는 원인·정상·복구 단정 0건, 중요한 실패·잘림 누락 0건, 사실 근거 참조 100%, Discord의 중요한 한계 보존을 확인한다. 구조 검증, 에이전트 의미 대조, 사람 검토와 제품 실행 검증을 별도로 기록한다.

## 두 출력 경로와 해석 경계

| 구분 | 현재 소유 계약 | 이 템플릿과의 관계 |
|---|---|---|
| 기존 P0 V1 | PRD 03의 `monitoring-report` 1.1.0과 PRD 06의 `ReportAgentInputV1` | Backend 5xx 전용 7필드. 상태별 고정 문구와 `run_`/`tc_`/`ev_` 참조를 유지한다. MySQL 사례를 강제 변환하지 않는다. |
| 1차 MVP | PRD 03·06의 MVP 절, `diagnosis-report/1.0.0` | `diagnosis_id`, 호출 메타데이터, 해석, 한계 등을 파일에 저장한 뒤 재조회해 요약과 첨부를 만든다. P0 전체 완료가 아니다. |
| 사람용 템플릿 v0.1 | 이 설계 문서 | 7구획은 읽기 순서다. 7필드와 일대일 대응하지 않으며 새 저장 필드나 모델 출력 필드를 승인하지 않는다. |

`success`는 호출 실행 성공이다. `investigation_complete`는 진단 에이전트의 조사 종료 이유다. 어느 값도 필수 검사 충족, 원인 확정, 전체 정상 또는 복구를 증명하지 않는다.

`seq`는 접수 순서이며 연속 관측 시간이나 인과 순서가 아니다. 실패 호출의 `observed_at`을 성공한 원천 측정 시각으로 표시하지 않는다.

## 상세 보고서 템플릿

보고서 머리에는 안전한 조사 이름, 같은 진단의 식별자, 보고서 생성 시각을 둔다. 생성 시각과 호출 기록 시각을 구분한다.

대상·증상·환경을 입력에서 확인할 수 없으면 미제공으로 표시하며 원래 요청문이나 환경값을 다시 가져오지 않는다.

**읽기용 배치**

- 7개 구획은 같은 수준의 제목으로 표시하고, 구획 사이에는 빈 줄과 구분선을 둔다.
- 관측 내용, 가설, 판단 한계는 문단을 나눈다. 근거 ID는 해당 문장과 같은 문단에 둔다.
- 여러 호출을 대조하는 사실·상세 근거는 표로, 병렬적인 확인 항목은 목록이나 표로 표시한다.
- 제목·본문·표·목록 사이에 빈 줄을 둔다. 단순 줄바꿈을 여러 번 넣어 여백을 대신하지 않는다.
- Discord도 핵심 발견, 중요한 한계, 후속 확인, 상세 안내 사이에 빈 줄을 둔다. 여백과 강조 기호를 포함해 길이를 검증한다.

### 1. 진단 요약

핵심 관측과 마지막 조회의 의미를 2~4문장으로 적는다. 가설 유무·원인 미확정 여부와 결론을 제한하는 실패·잘림을 함께 둔다.

정상/복구 배지를 새로 만들지 않는다.

문장 틀: “<허용된 관측>이 확인됐습니다. [call ID] <빈 결과·조회 실패·잘림> 때문에 <확인하지 못한 범위>가 남습니다. 원인은 <확정 근거가 없으면 미확정>입니다.”

근거가 메타데이터뿐이면 “조회가 성공해 N행을 반환했다”까지만 쓴다.

---

### 2. 조사 대상·범위

검증된 대상 별칭, 확인하려는 증상, 실제 호출·기록 시각, 관측 구간과 포함되지 않은 검사를 구분한다.

미제공 항목은 생략해 조사 범위를 넓게 보이게 하지 않는다. 도구 이름만으로 실제 서버·필터·전체 범위를 추정하지 않는다.

---

### 3. 확인된 사실

| 종류 | 사실 | 호출 근거 |
|---|---|---|
| 원천 관측 | 정제·타입·참조 검증을 통과한 값으로 조립한 문장 | 같은 진단의 call ID |
| 실행 기록 | 성공/빈 반환/시간 초과/잘림 등 실행기가 기록한 내용 | 같은 진단의 call ID |

각 사실 행에는 근거를 둔다. 복수 호출을 묶으면 그 호출을 모두 적는다. 숫자·단위·시각·범위는 입력과 일치해야 한다.

`diagnostic_comment.observation`은 이 표에 복사하지 않는다. 원천 관측이 없으면 실행 기록만 표시하고 그 한계를 적는다.

---

### 4. 원인 가설과 근거

가설마다 “가능성” 표시, 뒷받침하는 성공 관측, 반대되거나 설명하지 못한 관측, 확인에 필요한 정보를 연결한다. 실패 호출은 수집 공백의 근거이며 그 자체로 장애 원인의 근거가 아니다.

설명력이 부족하거나 관측이 상충하면 “현재 근거로 원인 가설을 제시하지 않습니다”를 허용한다. 모델의 `null`을 실패나 억지 가설로 대체하지 않는다.

이 절 전체를 모델에 작성시키지 않는다. 모델이 쓸 수 있는 값은 현재와 같이 `suspected_cause` 하나다.

근거 연결·반대 관측의 구조화 및 고정 한계 표시 방식은 후속 계약 대상이다. 가설 안에 ID가 있다는 사실만으로 내용의 타당성이 검증되지는 않는다.

---

### 5. 조사 한계·조회 실패

| 한계/실패 | 근거 | 판단에 미치는 영향 |
|---|---|---|
| 시간 초과 또는 권한 거부 | 해당 call ID와 안전한 코드/고정 설명 | 그 호출의 원천 상태를 확인할 수 없음 |
| 결과 잘림 | 해당 call ID | 반환 부분 밖의 존재·규모·분포를 알 수 없음 |
| 증상 연결·측정 구간 등 미제공 | 제공 자료의 범위 또는 해당 call ID | 원인·지속 시간·영향·복구 판단 불가 |

빈 결과는 실패로 바꾸지 않고, 실패는 0행으로 표시하지 않는다. `truncated=false`는 반환 잘림 표식이 없다는 뜻이며 완전 조사 증거가 아니다.

앞선 성공 관측은 뒤의 실패 때문에 제거하지 않는다.

---

### 6. 후속 확인 사항

확인 항목, 미확인 정보와의 연결, 확인 목적을 표로 적는다. 담당자의 검토 항목이며 자동 추가 호출·재시도·운영 조치가 아니다. 조사 권한이나 도구가 있다고 가정하지 않으며 실행 명령·SQL·URL·연결 종료를 제안하지 않는다.

사례별 구체적 문구는 설계 목표이고 현재 고정 `recommended_next_action`의 변경은 PRD 03에서 결정한다.

---

### 7. 호출별 상세 근거

접수 순서대로 call ID, 도구, 기록 시각, 성공/실패, 안전한 결과 요약, 잘림과 오류를 표시한다. 사실과 별도 표시한 진단 해석은 같은 호출에 연결한다.

원시 행·HTTP 본문·셸 출력·자유형 오류·요청/인수 원문은 포함하지 않는다. 사람이 읽는 상세 근거도 허용된 정제 근거의 표시이며 원시 덤프가 아니다.

## Discord 요약

저장 후 재조회한 동일 보고서에서 코드가 결정적으로 만든다. 새 모델 호출이나 새 결론은 없다.

MVP는 `diagnosis_id`와 `amdc-report.md`를 사용하고, 기존 V1의 Run 조회 안내와 혼합하지 않는다. 실제 MVP에 없는 REST 조회 URL을 만들지 않는다.

표시 순서 제안:

1. 조사 이름, 진단 ID, 조사 종료 설명과 호출 성공/실패 수
2. 핵심 사실과 해당 호출 ID
3. 원인 가설 또는 판단 보류, 중요한 실패·잘림·상충·근거 부족과 판단 영향
4. 후속 확인의 목적, 상세 첨부 안내, 생략한 호출 상세 개수

PRD 03의 1,900자 한도를 유지한다. 길이가 부족하면 반복 설명과 개별 호출 상세, 가설 부연부터 항목 단위로 생략한다. 중요한 한계는 고정된 짧은 문장과 영향을 받은 ID/개수로 남긴다. 여러 실패는 유형별로 묶되 실패 유형이나 결과 공백을 없애지 않는다. 사실이 줄어도 한계와 진단 식별자는 남아야 한다. 한계를 포함한 필수 요약도 한도에 맞출 수 없으면 조용히 자르지 않는 실패 정책을 PRD 03에서 확정한다.

현재 `mvp-discord-formatter.ts`는 한계 목록을 360자로 미리보기하고 호출 두 건만 표시한다. 따라서 모든 입력에서 위 보존 기준을 충족한다고 주장할 수 없다.

네 문서 예시의 길이 통과는 현재 포매터나 최악 크기 입력의 검증 결과가 아니다.

## 구획별 입력과 작성 책임

현재 제공 여부는 `src/report-agent/mvp-report.ts`의 `execution`, `parseHandoff`, `createMvpReport`와 `src/reports/mvp-discord-formatter.ts`를 기준으로 한다. 아래 “필요 입력”은 의미 요구사항이며 확정 DTO 필드명이 아니다.

### 입력·책임: 진단 요약

- **필요한 입력:** 검증된 핵심 사실, 조사 종료 설명, 중요한 한계
- **현재 제공 정보와 공백:** 호출 수·성공/실패·종료 이유·일반 한계는 있음. 도메인별 사실과 증상 연결은 없음
- **작성 책임:** 코드는 사실·한계 요약, 모델은 가설 한 필드만
- **후속 소유 계약:** PRD 03·06

### 입력·책임: 조사 대상·범위

- **필요한 입력:** 안전한 대상/증상, 검사 목적·조건, 측정 구간·누락 검사
- **현재 제공 정보와 공백:** tool/plugin/기록 시각은 있음. request/input은 투영 제외. 대상·필터·측정 구간·필수 검사 충족은 모름
- **작성 책임:** 코드가 검증된 메타데이터만 표시. 모델 추정 금지
- **후속 소유 계약:** PRD 00·02·05·06

### 입력·책임: 확인된 사실

- **필요한 입력:** 도구별 정제 값·단위·출처·같은 진단의 call ID
- **현재 제공 정보와 공백:** MySQL은 반환 행 수·잘림만 있음. HTTP는 상태 코드, shell은 종료 코드만 있음. MySQL 잠금 관계·내용은 없음
- **작성 책임:** 정규화/검증 뒤 코드 조립. comment는 해석으로 분리
- **후속 소유 계약:** PRD 03·05·06

### 입력·책임: 원인 가설과 근거

- **필요한 입력:** 허용 관측, 찬성·반대 근거, 미확인 정보
- **현재 제공 정보와 공백:** `diagnostic_comment`, 관련 ID는 있음. 사실성/인과관계 검증은 아님. 모델은 `suspected_cause` 또는 null 반환
- **작성 책임:** 모델 권한 유지. 코드가 참조/표시·한계 보존, 의미는 별도 검토
- **후속 소유 계약:** PRD 03·06

### 입력·책임: 조사 한계·조회 실패

- **필요한 입력:** 호출별 오류, 잘림, 수집 공백과 결론 영향
- **현재 제공 정보와 공백:** 오류 코드·잘림 요약·일반 limitations 있음. 완전성/상충/영향의 typed 계약은 없음
- **작성 책임:** 코드가 결정적으로 표시. 모델의 한계 누락으로 삭제되지 않음
- **후속 소유 계약:** PRD 03·06

### 입력·책임: 후속 확인 사항

- **필요한 입력:** 미확인 항목과 확인 목적의 검증된 대응
- **현재 제공 정보와 공백:** 상태별 코드 문구 있음. 연결/트랜잭션별 구체 문구는 없음
- **작성 책임:** 코드 정책. 모델이 조치·도구 호출을 생성하지 않음
- **후속 소유 계약:** PRD 02·03

### 입력·책임: 호출별 상세 근거

- **필요한 입력:** 순서·ID·도구·기록 시각·정제 결과·실패·해석 구분
- **현재 제공 정보와 공백:** 메타데이터와 해석은 있음. 원천 세부 사실·원천 계약 버전은 없음
- **작성 책임:** 코드가 검증·조립하고 저장된 객체에서 표시
- **후속 소유 계약:** PRD 03·05·06

### 입력·책임: Discord

- **필요한 입력:** 저장된 핵심 사실·중요 한계·안전한 생략 정보
- **현재 제공 정보와 공백:** 저장/재조회·첨부 있음. 360자 한계 미리보기의 중요도 보존은 미보장
- **작성 책임:** 코드 전용 투영
- **후속 소유 계약:** PRD 03·04

현재 입력만으로 쓸 수 있는 문장: “call-1은 조회에 성공해 1행을 반환했습니다.” 쓸 수 없는 문장: “연결 386이 382를 기다렸습니다.”

후자는 전용 정규화기가 검증한 잠금 관계가 있어야 한다. 코멘트에 번호가 적혀 있어도 차이를 메우지 못한다.

## 미결정 계약

| 결정 | 다음 검토에서 구체화할 내용 | 결정 위치·검토 역할 |
|---|---|---|
| 정제된 MySQL 근거 | 허용 사실 종류·타입·값/관계 검증, 안전한 식별자 치환과 동일성 범위, 원천 계약 버전, 항목·전체 크기 상한 | PRD 03·05·06, 생산자/Tool Core와 Report 담당 |
| 조사 범위·시간 | 대상 별칭·증상 요약의 허용 여부, 필터/관측 구간의 안전한 표현, 기록 시각 의미, 필수 검사·완전성·상충 판정 | PRD 00·02·05·06, 시나리오/생산자 담당 |
| 저장·표시 연결 | 현재 MVP의 확장 여부와 정확한 버전, 승인된 사실/한계/가설 근거의 영속 표현, 구버전 거부·호환 정책 | PRD 03·06. P0 Run/SQLite 변경이 필요하면 PRD 01도 별도 검토 |
| 요약·후속 확인 | 사실 기반 요약과 한계별 확인 항목, Discord 필수 정보·생략 순서·초과 시 동작 | PRD 03·04, Report 담당과 Discord 통합 검토자 |

권고는 정제된 근거 계약을 먼저 닫고 코드 조립을 확장하는 것이다. 모델 권한 확대와 원시 결과 재유입은 이 권고에 포함되지 않는다.

숫자 상한·새 스키마 버전·필드명·신규 MySQL 판정은 이 문서에서 확정하지 않는다. 필요한 사용자/계약 담당자 결정이 남으면 해당 구현 게이트를 열지 않는다.

## 검증과 인계

검증 단위는 사례 A~D의 입력표, 상세 보고서, Discord 요약과 현재 입력 표현이다. 문서 예시는 제품이 실제 생성한 출력이나 실행 가능한 `DiagnosisHandoff` fixture가 아니다.

| 검증 종류 | 점검할 것 | 판정 범위 |
|---|---|---|
| 자동 구조 점검 | 4사례 × 7구획, 보고서 머리말의 조사 이름·진단 ID·생성 시각, 사실 행·요약 문단의 호출 참조와 사례 내 일치, Discord 1,900자, 필수 실패·잘림 표식, 링크, 요약 200자 | 문서 구조·표식만. 자유형 문장의 인과 타당성은 증명하지 않음 |
| 에이전트 의미 대조 | 모든 관측의 값·시각·범위와 근거 비교, 빈 결과/실패 구별, 상충 보류, 가설/미확인 구별, 한계 누락 | 고정 문구를 읽어 대조한 결과. 사람 승인이나 모델 품질 평가가 아님 |
| 사람의 의미 검토 | 정제 근거 가정과 표현의 이해 가능성, 후속 계약 수용 여부 | 구조·배치는 사용자 합의 완료. 사례별 의미 검토와 후속 계약 승인은 남음 |
| 제품 검증 | 정규화·모델·저장·포매터의 실제 산출물과 fixture 비교 | 이번 작업에서 실행하지 않음. 후속 구현의 PRD 04 대상 |

이번 문서 검증 결과와 재현 방법은 [사례 문서의 검증 기록](report-template-v0.1-examples.md#검증-기록)에 둔다. 제품 테스트·성능·실 원천/LiteLLM/Discord 검증으로 확대 해석하지 않는다.

다음 채팅 하나의 산출물은 **정제된 근거 입력 계약 설계**다. 위 미결정 표를 소유 PRD에 연결해 허용 필드·신뢰 경계·정규화·크기·버전·실패·호환 정책과 네 사례의 생산자→소비자 대응을 검토 가능한 계약안으로 만든다.

먼저 설계를 닫고 구현 필요 범위를 정한다. 이번 템플릿만으로 제품 코드를 시작하지 않는다.

다음 작업의 성공 기준: 네 사례의 사실·실패·잘림·상충을 손실 없이 표현할 수 있고, 원시 결과/미검증 코멘트의 사실 승격 경로가 없으며, 누락·다른 진단 ID·잘못된 타입·상한 초과를 거부하는 검증 계획과 계약 담당 결정이 명시돼야 한다.

미승인 계약은 미결정으로 남긴다. [이슈 #7](https://github.com/Aolda/amdc/issues/7)과 [PR #17](https://github.com/Aolda/amdc/pull/17)을 연결하되 이 문서 완료를 이슈 종료·PR 병합·P0 완료로 표시하지 않는다.
