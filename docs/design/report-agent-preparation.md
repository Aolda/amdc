## 문제와 이번 작업의 범위

사용자가 제공한 현재 구조는 Discord 요청, LangChain 진단, YAML Tool Core와
system/prometheus/mysql/proxysql 조회까지를 설명한다. Report Agent는 앞으로 붙일
구성요소다. 기록 양식에는 호출 결과와 관찰·가설·한계가 있지만, 기존 PRD의
Backend 5xx 전용 Evidence와 직접 호환되지 않는다.

이번 결과는 현재 구조 기록, 양식 전사·필드 검토, 설계 대안 및 검증 시나리오다.
제품 코드·스키마·DB·배포·Notion은 변경하지 않는다. 문서 변경만 되돌리면 롤백된다.
성공 기준은 첨부 필드 누락 0개, 미확정 계약을 구현 완료로 표현한 항목 0개,
기존 계약과의 주요 충돌에 소유 PRD와 다음 결정이 모두 연결되는 것이다.

## 기존 계약과의 차이

| 논점 | 최신 자료 | 기존 계약 | 다음 결정 / 소유 |
|---|---|---|---|
| 도구 노출 | 선택 플러그인과 YAML 정의 | TypeScript 정적 3도구 | YAML을 정적 등록원으로 인정할 조건 / PRD 00·02 |
| 대상 원천 | system, prometheus, mysql, proxysql | Prometheus, Loki, Backend의 고정 매핑 | 새 도구별 source contract와 Loki 위치 / PRD 05 |
| 시나리오 | MySQL이 느리다는 자유형 요청 | backend_5xx_increase 하나 | MySQL 지연의 검사 범위·문제 판정 / PRD 00·02 |
| 기록 | result.rows + 모델 comment | typed Evidence + DiagnosisResult | 진단 envelope와 손실 없는 변환 / PRD 06·03 |
| 저장소 | PostgreSQL 지식 DB 테스트 | SQLite Run/Evidence/Report | 지식과 실행 이력의 저장 책임 분리 / PRD 01 |
| 보고서 | 조회 결과·의심 지점 전달 예정 | 모델은 suspected_cause만 작성 | 한계 표현 위치와 모델 출력 범위 / PRD 03·06 |
| 채널 | Discord 임시 결과 | 정본 영속화 후 최종 전달 | 기존 Gateway 유지, 전달 접점 교체 / PRD 03·06 |

이번 작업은 최신 자료를 보존하되 기존 계약을 몰래 교체하지 않는다.
특히 PostgreSQL 지식 DB 존재는 SQLite 실행 저장소 폐기의 근거가 아니다.
Backend 전용 ‘세 required check’ 정상 문구를 MySQL 보고서에 그대로 쓰면 안 된다.

## 대안 비교

| 접근 | 장점 | 실패 모드 | 판단 |
|---|---|---|---|
| 진단 JSON 전체를 모델에 주고 최종 보고서 작성 | 빠른 연결, 표현 자유 | 원시 데이터 노출, 상태 조작, 추적 끊김, 과장된 원인 | 채택하지 않는 안 |
| 검증된 기록 → 정규화/참조 검증 → 제한된 Report Agent → 결정적 조립 | 증거 추적과 기존 권한 경계 보존 | 새 도구 스키마·시나리오 정합화가 선행되어야 함 | 권장 설계 방향 |
| 모델 없이 결정적 템플릿만 사용 | 재현과 비교가 쉬움 | 여러 호출의 가설 종합이 제한됨 | 품질·비용 비교 기준선 |

권장 방향은 구현 승인 전 설계 제안이다. 전용 MySQL 계약이 없는 현재 상태에서
기존 V1 어댑터가 이 예시를 수용한다고 가정하지 않는다.

## 권장 처리 흐름

~~~text
진단 실행 종료
→ AMDC가 기록의 버전·완료 상태·크기·정제 여부 확인
→ 도구별 정규화 + 같은 Run 호출/증거 참조 검증
→ 시나리오별 결과 해석기
→ Report Agent에 필요한 검증된 최소 입력 조립
→ 도구 없는 원인 초안
→ 결정적 보고서 조립·검증·영속화
→ 저장된 리포트의 Discord 표시
~~~

진단 Agent는 관측을 해석하고 가설을 낸다. Report Agent는 그 가설을 그대로
확정하지 않고 근거가 허용하는 범위의 설명만 만든다. 관찰 사실과 판정,
상관관계와 인과관계, 수집 실패와 정상 빈 결과를 구별한다.

현재 모델 출력 범위는 [PRD 06의 Report Agent 실행 계약](../prd/current/06-diagnostic-agent-tool-runtime.md#report-agent-실행-계약)을 유지한다.
한계·후속 조치까지 모델이 작성하도록 넓히려면 PRD 03·06 개정과 검증이 먼저 필요하다.
구현 시 기존 예산을 그대로 참조하며 별도 값으로 복제하지 않는다.

## 예시가 허용하는 보고서 내용

아래는 운영 리포트 또는 기존 7필드 스키마의 유효 예시가 아닌 내용 검토용이다.

- 관측 사실: call-001에서 연결 386이 382의 잠금 해제를 기다리는 행이 조회됐다.
- 가설: 이 잠금 대기가 지연에 영향을 주었을 가능성이 있다.
- 한계: 지속 시간, 영향 범위, 382가 잠금을 유지한 이유는 이 조회만으로 알 수 없다.
- 추가 설계 대상: 관련 트랜잭션·관측 시간 범위를 담당자가 확인할 수 있도록 근거를 연결한다.

‘382가 전체 장애의 원인이다’, ‘교착 상태다’, ‘연결을 종료하면 해결된다’는
현재 예시로 뒷받침되지 않는다. 실행 조치나 추가 도구 호출을 자동으로 만들지 않는다.
한계의 최종 노출 위치는 고정 문구·별도 검증된 필드 중 무엇을 쓸지 아직 결정해야 한다.

## 결정 순서와 준비 완료 조건

| 순서 | 닫을 결정 | 검토 역할 | 산출물 |
|---|---|---|---|
| 1 | 첨부 양식을 생산자 v1로 발전시킬지, 기존 DiagnosisResult를 유지할지 | 진단 생산자 재경 + 리포트 소비자 동훈 | 버전이 있는 성공·오류·부분 결과 예시 |
| 2 | MySQL 지연을 첫 연결 시나리오로 채택할지 | 시나리오/Tool Core 담당 | 필수 검사·판정·원천 스키마 |
| 3 | 기록 저장소와 Run/diagnosis/call 대응, 정제·보존 | AMDC 저장/보안 경계 담당 | PRD 01·03·06의 일치하는 계약 |
| 4 | 최종 보고서에서 관측·가설·한계를 표현할 방식 | Report Agent 담당 | 출력 예시와 모델/결정적 필드 구분 |

역할은 기존 소유권을 따른 검토 제안이며 새 작업 배정이나 GitHub 상태 변경이 아니다.
1–4와 크기·시간·완료 조건을 닫고 테스트 기반을 확보한 뒤 구현 게이트를 재평가한다.
현재 PRD가 언급하는 report-agent-input/output 및 narrative 스키마 파일은 이 로컬
checkout에 없으므로 문서 속 경로만으로 검증기를 사용할 수 있다고 판단하지 않는다.

## 검증 시나리오와 성공 기준

이 표는 후속 개정의 인수 기준 제안이며 실행한 테스트 결과가 아니다.
기존 P0 검증의 정본은 [PRD 04](../prd/current/04-verification-and-handoff.md)다.
가짜 도구·가짜 모델·가짜 Discord와 격리된 임시 저장소로 검증한다.

| 입력/실패 | 기대 결과 |
|---|---|
| 첨부 성공 1건 | 자기 call ID와 행 값을 보존하고 가설을 사실로 승격하지 않음 |
| 빈 rows | 해당 시점·해당 도구의 결과 부재만 표현; 전체 정상 추론 0건 |
| truncated=true 또는 부분 진단 | 불완전 범위를 보존; 완전한 검사로 표시한 결과 0건 |
| 성공 뒤 timeout/권한 거부 | 실패도 순서대로 남고 성공 근거를 덮어쓰지 않음 |
| 중복 seq/call ID, 없는 ID, 다른 Run ID | 제공자 호출 전 거부 100%, 임의 재번호/참조 복구 0건 |
| comment가 result와 다른 연결 번호 주장 | 사실 검토에서 차이를 발견; 모델 문장을 정본 사실로 복사 0건 |
| 지시문·비밀정보가 request/input/rows/comment에 포함 | 지시 실행 0건; 주입 비밀정보의 저장·외부 전송 0건 |
| 상한 초과·알 수 없는 버전·잘못된 타입/시각 | 검증 거부 100%, 무제한 모델 입력 0건 |
| Report 모델 실패·저장 실패 | 완료 리포트와 Discord 리포트 전달 0건 |
| 저장 후 Discord 실패 | 저장된 결과 불변, 자동 재전달 0건 |
| 동일 진단 중복 완료·지연 콜백 | 최종 저장 1건 이하, 중복 전달 0건 |

자유형 문장의 사실 일치율은 JSON Schema만으로 보장하지 않는다.
고정 fixture의 주장/근거 대조와 사람 검토를 별도 평가하고,
정본 관찰 문장은 검증된 구조화 값에서 결정적으로 만든다.

새 envelope의 최대 관찰 수·행 수·항목/전체 바이트와 실패 정책은 구현 전 수치로 확정한다.
기존 Report Agent 호출 예산은 PRD 06, 종단 간 p95·동시성·RSS·롤백 기준은 PRD 04를
기준선으로 삼는다. 새 양식 검증에는 p50/p95/p99, 최대 크기, 10개 동시 진단의 혼입,
1,000개 진단 후 RSS를 함께 측정하며 기준 변경은 해당 소유 PRD에서 결정한다.

## 2026-09-22 후속 합의: 선행 개발과 템플릿 논의 분리

사용자는 팀원의 진단 실패·종료 상태 답변을 기다리는 동안 독립 개발을 시작하고,
최종 리포트 형식·템플릿은 별도 세션에서 논의하기로 했다.
전체 연동은 ready_for_design이며, 아래 제한된 선행 개발만 ready_for_implementation이다.
앞선 “제품 코드 변경 없음”은 최초 문서 반영 작업의 범위다. 이 후속 합의는 새 구현 작업에 적용한다.

### 선행 개발 PAAR

- Problem: 진단 생산자의 오류/부분 결과 계약 미확정 때문에 리포트 개발 전체가 대기하고 있다.
- Analysis: 실제 진단 JSON에 직접 결합하면 생산자 변경이 내부 구현까지 전파된다.
  기존 PRD 06 소비자 계약과 가짜 입력을 기준으로 리포트 포트를 분리하면 검증을 먼저 진행할 수 있다.
  가짜 입력은 상위 계약 합의나 운영 연동의 증거로 사용하지 않는다.
- Action: 도구 없는 Report Agent 포트, 주입 가능한 모델 어댑터, 초안/포트 출력 검증기,
  해당 모듈만 검증하는 테스트 기반을 구현한다. 제공자는 가짜 구현으로 검증하고 실 API 호출은 하지 않는다.
- Result: 유효 초안/null 수락, 추가/누락 필드·길이 초과·잘못된 버전/Run·비밀정보 거부,
  시간 초과/제공자 실패 재현, 자동 재시도와 도구 호출 0회를 증명한다.

### Implementation Scope

- Files/modules: src/report-agent/**, 필요한 최소 schemas/report-*.schema.json,
  tests의 리포트 전용 fixture/unit 테스트, package.json 및 필요한 테스트 설정.
  실제 경로는 새 세션에서 기존 파일과 지침을 확인하고 확정한다.
- Interfaces/contracts: 기존 PRD 06 ReportAgentPort, ReportNarrativeDraftV1,
  ReportAgentOutputV1과 필요한 기존 소비자 입력 검증. 가짜 입력에도 동일 검증을 적용한다.
  모델 필드는 suspected_cause 하나이며 null을 허용한다.
- Explicit non-goals: 진단 내부/YAML 변경, 신규 생산자 오류 enum 확정, MySQL 판정,
  실제 진단 변환 어댑터, Run/DB 저장 구조 변경, 운영 진입점 연결, 실 OpenAI/AMDB/Discord 호출.

## 2026-09-25 생산자 인계 확인과 Report 경계

확인 대상은 미병합 [PR #14](https://github.com/Aolda/amdc/pull/14)의

읽은 결과다. 병합·운영 동작·정본 P0 계약 승인을 뜻하지 않는다.

| 질문 | PR #14에서 확인한 동작 | Report 측 적용 |
|---|---|---|
| 도구 실패 | `observations[].status`는 `success | error`; 성공은 `result`와 `error: null`, 실패는 `result: null`과 정제된 오류다. 실패 코드에 `tool_timeout`과 `source_permission_denied`가 있다. | 실행 성공을 정상 판정으로 바꾸지 않는다. 기존 V1 도구 오류 코드와 이름이 같아도 저장된 오류의 동일성을 검증하기 전에는 변환하지 않는다. |

| 근거 연결 | AMDC가 wrapper 진입 시 `diagnosis_id:call-N`을 예약한다. 성공과 실패를 같은 배열에 넣고 `seq`로 접수 순서대로 조립한다. 모델은 실제 ID에만 주석·관련 호출을 달 수 있으며 없는 ID, 중복, 자기 참조를 거부한다. | `seq`는 완료 시각이나 인과 순서가 아니다. `diag-...:call-N`을 정본 `tc_...`/`ev_...`로 접두사 변경하지 않고, 저장된 동일 Run 호출 원장에서 대응을 증명한다. |

기존 `ReportAgentInputV1`은 `backend_5xx_increase`의 영속화된 Evidence/Tool Error와
`run_`/`tc_`/`ev_` 식별자를 요구한다. PR #14 인계는 버전이 없고 원천 결과를 담으며
Run ID·정본 Evidence 대응·전체 크기 상한이 확인되지 않았다. 따라서 현재 소비자
포트에 직접 공급하지 않는다. 이번 로컬 report 테스트는 생산자 모양을 V1로 넣으면
제공자 호출 전에 거부하고, 정본 V1의 성공→권한 오류→성공 원장 순서를 검증한다.

다음 연결 계약은 생산자/저장 경계가 소유한다. `diagnosis_id`와 영속 Run의 일대일 대응,
호출 ID의 정본 매핑, 오류 코드별 의미, 정상 빈 결과와 미수집 범위, 완료·부분·인계
생성 실패의 결정적 분류, 결과별 정제·크기 상한 및 source contract 버전을
버전이 있는 DTO와 가짜 실행 검증으로 확정해야 한다. 그 후 시나리오별 해석기를
거쳐 최소한의 검증된 입력만 Report Agent에 전달한다. MySQL 원시 행이나 모델
comment를 Evidence 또는 최종 7필드 사실로 직접 복사하지 않는다.
