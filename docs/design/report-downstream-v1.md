# Report V1 후단 선행 구현

기존 Backend 5xx V1 계약에서 결과 판정·7필드 조립·검증과 Discord 텍스트 투영을 가짜 산출물로 먼저 구현한다. 진단 인계, DB 완료 커밋, 실제 전달은 후속 연결이다.

상태: 제한된 후단 구현 설계 · 현재 7필드 V1에만 적용
기준일: 2026-09-25
정본 계약: [PRD 02](../prd/current/02-agent-tool-core-and-scenario.md#결과-판정기), [PRD 03](../prd/current/03-evidence-report-security.md#report-계약), [PRD 06](../prd/current/06-diagnostic-agent-tool-runtime.md#reportagentinputv1)

PR #14의 생산자 인계와 PR #15의 진단 지식 DB는 이 순수 후단의 입력 계약이 아니다. 두 PR이 병합돼도 새 시나리오의 정본 Evidence·Run 대응과 저장 트랜잭션이 자동으로 생기지는 않는다.

## PAAR 및 선택

- Problem: Report Agent가 만든 `suspected_cause` 본문은 상태·관찰 근거·후속 조치가 없는 초안이어서 정본 리포트로 저장할 수 없다.
- Analyze: 생산자의 원본 `DiagnosisHandoff`에서 바로 보고서를 만들면 PR #14의 미병합 형식과 원천 결과에 결합한다. 검증된 V1 Evidence/Tool Error와 저장된 호출 원장에서 결정적으로 조립하면 현재 정본을 가짜 입력으로 검증할 수 있다. 모델이 7필드를 모두 작성하는 안은 상태와 근거를 바꿀 수 있어 제외한다.
- Action: PRD 02의 V1 결과 우선순위, PRD 03의 고정 문구·관찰 문장·정본 스키마와 1,900자 Discord 투영을 독립 함수로 구현한다. 입력과 출력은 기존 소비자 검증을 다시 통과하며, 기대 상태와 계산 상태가 다르면 거부한다. 실제 DB·Discord·진단 런타임은 호출하지 않는다.
- Result: 양성 우선, 권한 부족, 유효한 세 음성, 시간 초과/범위 부족의 네 상태와 성공·오류 혼합 호출 순서를 가짜 산출물로 재현한다. 상태/Run/근거/문구/비밀정보 변조는 저장 전 거부하고, Discord 내용은 1,900자 이내·항목 경계 생략·정확한 누락 개수를 확인한다. 전체 테스트·타입 검사·빌드를 통과한다.

## 경계와 연동 순서

`ReportAgentInputV1` + 저장된 호출 원장 + `ReportAgentOutputV1`에서 정본 7필드를 조립한다. 두 인계 객체의 정확한 버전과 동일 Run 참조를 검증하며, 호출 원장이 모든 Evidence/Tool Error의 멤버십과 순서를 증명해야 한다. 결과 판정은 PRD 02의 현재 시나리오만 지원하고, 리포트 문구는 PRD 03 스키마 1.1.0 상수와 일치해야 한다.

실제 연결 시에는 먼저 Evidence/Tool Error 커밋을 확인하고, `problem_detected`에서만 Report prompt binding 뒤 모델을 호출한다. 조립·검증 결과는 이후 PRD 01의 리포트 삽입과 `running -> completed` CAS를 한 트랜잭션에 넣는다. Discord는 커밋 뒤 저장소에서 다시 읽은 리포트만 받는다. 이 문서와 순수 함수 테스트가 그 트랜잭션·전달을 구현했다는 뜻은 아니다.

Discord 투영 함수는 호출자가 다시 읽어 제공한 7필드 객체와 Run ID만 받는다. 상태·요약·Run ID는 필수이고, 탐지 문제·관찰 결과·원인 가설 미리보기·후속 확인·권한 플래그를 정본 필드 순서로 표시한다. 원인 가설 미리보기는 최대 300개 유니코드 코드 포인트에서 줄임표로 자르고, 관찰 결과는 항목 전체만 포함한다. 빠진 관찰 결과 수와 Run ID 조회 안내를 표시한다. 이 함수는 저장 여부나 같은 Run 소속을 스스로 증명하지 않으므로, 실제 Discord 접점은 완료 커밋 뒤 저장소 읽기와 전달 소유권 확보를 먼저 강제해야 한다.

## 범위와 롤백

새 코드는 `src/reports/`와 가짜 산출물 테스트에 한정한다. 현재 V1 스키마·고정 문구, Report Agent 모델 호출 예산, 진단/YAML, MySQL 시나리오, 지식 DB, Run 저장 구조는 변경하지 않는다. 운영 진입점에 연결하지 않은 모듈과 테스트만 제거하면 롤백된다.

## 다음 연결 게이트: 저장·Discord 접점

현재 순수 함수의 ID 대조는 저장된 Evidence/Tool Error 본문과 `ReportAgentInputV1`의 동일성을 증명하지 않는다. 이번 실패 주입은 양성 Evidence 뒤 권한 거부를 관찰 결과에 남기면서 `problem_detected` 우선순위를 유지하고, `secret_exposure_risk` 오류가 앞선 양성 결과보다 우선해 리포트를 차단하는지 확인한다. Discord 최종 비밀정보 검사기가 실패하면 전송 문장 대신 안전한 `discord_format_failed`만 던지는지도 확인한다. 이 검증은 실제 저장·전달의 인수 증거가 아니다.

연결 단계의 Problem은 메모리 내 조립 성공을 완료 Run 또는 Discord 전달로 오인할 위험이다. 두 경로를 비교한다. 호출자가 조립 객체를 곧바로 Discord에 넘기는 경로는 완료 커밋 실패와 지연 콜백에서 미저장 내용을 보낼 수 있다. 저장소가 동일 Run 산출물 읽기, 완료 트랜잭션, 완료 후 다시 읽기를 소유하는 경로는 PRD 01·03의 순서를 보존하지만, 현재 코드에 그 저장소 포트와 실제 상호작용 소유자가 없다. 따라서 운영 호출 사슬을 바꾸는 PAR와 가짜 실패 주입 인수 조건을 먼저 확정한다.

최소 인터페이스 결정 입력은 다음과 같다.

1. 저장소 포트의 동일 Run 읽기 결과: `runs.started_at`, 호출 순서, 검증·커밋된 Evidence/Tool Error 본문과 ID, `report_prompt_version`을 어떤 원자적 읽기 또는 일관성 경계에서 반환할지. 단순 ID 원장만으로 본문 동일성을 주장하지 않는다.
2. 완료 포트: PRD 01의 `BEGIN IMMEDIATE` 안에서 7필드 Report 삽입과 `running -> completed` CAS를 누가 소유하고, 실패 뒤 별도 `failed/storage_failure` 전이와 fail-stop을 누가 수행할지. 읽기와 완료 사이의 중복/지연 콜백 승자도 정해야 한다.
3. 전달 포트: 완료 Run에 속한 정확한 저장 객체를 다시 읽는 API, 프로세스 로컬 동일 Discord 상호작용의 `claimOnce` 토큰 생성·전달 주체, 훅 만료와 API 거부/응답 모호성의 이벤트 분류·관측 기록 소유자. 현재 포매터는 저장 여부와 상호작용 동일성을 스스로 증명하지 않는다.

PAR의 측정 가능한 Result는 가짜 저장소·전송기로 완료 커밋 전 API 호출 0, 같은 상호작용 중복/지연 콜백의 추가 호출 0, 완료 트랜잭션 실패 시 Report 0과 `completed` 전이 0, 커밋 후 포매터·Discord 실패 시 완료 Run/Report 변경 0, 자동 재전달 0을 확인하는 것이다. 이 접점은 위 소유권과 인수 범위가 정해지기 전까지 설계 상태로 둔다. PR #14 생산자 인계와 새 7구획 상세 보고서는 별도 계약이다.

합의한 새 7구획 상세 보고서는 [별도 논의 문서](report-template-discussion-2026-09-22.md#합의한-기본-방향)의 방향이다. 기존 7필드 V1과 저장 형태가 다르므로 이 구현으로 대체하거나 완료를 선언하지 않는다.
