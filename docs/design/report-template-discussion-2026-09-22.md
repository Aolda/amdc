상세 보고서의 7개 구획과 Discord 요약을 기본 방향으로 합의했다. 이 문서는 여러 호출·빈 결과·부분 조회 실패의 가상 예시를 비교하는 제안이며, 구현 계약과 생산자 실패 형식은 변경하지 않는다.

기준일: 2026-09-22
상태: 기본 방향 합의 · 사례와 세부 표현 검토안
범위: 이 작업 전용 제안 문서. 공통 PRD 및 제품 코드의 정본 계약을 대체하지 않는다.

## 합의한 기본 방향

사용자는 상세 보고서를 B안, Discord 요약을 A안으로 구성하는 기본 방향과 아래 7개 구획에 동의했다.

1. 진단 요약
2. 조사 대상·범위
3. 확인된 사실
4. 원인 가설과 근거
5. 조사 한계·조회 실패
6. 후속 확인 사항
7. 호출별 상세 근거

상세 보고서를 기준으로 Discord의 핵심 발견, 원인 확정 여부, 중요한 한계, 후속 확인과 상세 조회 안내를 만든다. 요약에서 새로운 결론을 생성하거나 중요한 조회 실패를 숨기지 않는다.

위 7개 구획은 사람이 읽는 구성이다. 기존 리포트 스키마의 7필드와 일대일로 대응한다고 결정하지 않았다. 각 구획의 저장 방식, 문장 생성 책임과 분량은 미확정이다.

이번 문구 제안은 다음과 같다.

- 정보가 없으면 해당 구획에 확인되지 않은 내용과 판단의 영향을 적는다.
- 상세 근거는 정제된 허용 결과와 호출 ID를 담는다. 원시 응답·질의·인증정보를 복사하지 않는다.
- 같은 사실을 요약·본문·근거에 표시하더라도 각각 핵심 전달, 판단 설명, 원자료 대조라는 역할을 구분한다.
- 후속 확인은 담당자가 검토할 항목과 확인 목적을 연결한다. 자동 추가 조회나 변경 조치를 요청하는 실행 인터페이스가 아니다.

## 예시 자료와 비교 조건

사용자 제공 예시에서 가져온 것은 다음 한 건이다. 이 원본도 실제 운영 기록이 아니라 사용자 제공 예시다.

- 호출 ID: `call-001`
- 도구: `mysql_get_lock_waits`
- 관측 시각: `2026-09-18T10:00:00Z`
- 결과: `waiting_connection_id=386`, `blocking_connection_id=382`
- 지연 관련성은 가설이며, 382의 잠금 유지 이유는 확인되지 않았다.

이하 `call-002`와 `call-003`의 시각·결과는 표현 검토를 위해 추가한 가상 자료다. 사례 A와 B는 각각 독립된 가상의 조사이며, 같은 호출 ID를 두 조사 사이에서 연결하지 않는다.

| 호출 | 도구 | 시각(UTC) | 사례 A의 가상 자료 | 사례 B의 가상 자료 |
|---|---|---|---|---|
| call-001 | mysql_get_lock_waits | 10:00:00 | 사용자 제공 예시: 386이 382의 잠금 해제를 기다리는 행 | A와 동일 |
| call-002 | mysql_get_lock_waits | 10:01:00 | 같은 연결 번호 조합의 대기 행 | A와 동일 |
| call-003 | mysql_get_lock_waits | 10:02:00 | 성공적으로 반환된 빈 행 목록 | 제한 시간 내 결과를 얻지 못함 |

시각은 모두 2026-09-18이다. B의 마지막 시각은 가상의 실패 기록 시각이며, 관측 성공 시각을 의미하지 않는다. 실제 생산자의 시간 필드나 오류 enum을 정한 것이 아니다.

정상 반환된 빈 행 목록, 반환 실패, 전체 조사 완료는 별개의 정보다. 두 사례 모두 전체 진단의 종료·완료 표식은 제공되지 않았다고 가정한다. 성공한 호출 수만으로 조사 완료나 보고서 발행 가능 여부를 결정하지 않는다.

아래 보고서와 Discord 문장은 읽기용 모형이다. 현재 V1 스키마의 유효 출력이나 실행 가능한 테스트 fixture가 아니다. Discord의 정본 `status` 값과 실제 `run_id` 바인딩은 MySQL 판정·인계 계약 합의 후 적용할 대상이며, 여기서는 새 상태를 만들지 않는다.

## 사례 A: 여러 조회 후 마지막 결과가 빈 경우

### 1. 진단 요약

앞선 두 조회에서 연결 386이 연결 382의 잠금 해제를 기다리는 행이 확인됐습니다. 마지막 조회에서는 잠금 대기 행이 반환되지 않았습니다.

잠금 대기가 요청된 MySQL 지연과 관련됐을 가능성은 있으나, 현재 자료로 원인을 확정할 수 없습니다. 마지막 빈 결과만으로 지연 증상이 해소됐다고 판단할 수는 없습니다.

### 2. 조사 대상·범위

- 요청된 증상: “MySQL이 느린 것 같아”
- 검토 자료: 2026-09-18 10:00, 10:01, 10:02 UTC의 잠금 대기 조회 3건
- 확인 범위: 각 조회 시점에 도구가 반환한 잠금 대기 관계
- 포함되지 않은 정보: 실제 요청 지연의 측정값, 지연 요청과 연결 번호의 대응, 트랜잭션 상태, 전체 조사 종료·완료 정보

세 시점의 자료이며, 그 사이의 상태를 연속 관측한 기록은 아닙니다.

### 3. 확인된 사실

| 관측 시각(UTC) | 확인된 사실 | 호출 근거 |
|---|---|---|
| 10:00:00 | 연결 386이 382의 잠금 해제를 기다리는 행이 반환됐습니다. | call-001 |
| 10:01:00 | 같은 연결 번호 조합의 대기 행이 반환됐습니다. | call-002 |
| 10:02:00 | 잠금 대기 행이 반환되지 않았습니다. | call-003 |

### 4. 원인 가설과 근거

가능성: 관측된 잠금 대기가 MySQL 지연에 영향을 주었을 수 있습니다.

근거는 두 시점에서 확인된 대기 관계입니다. [call-001, call-002] 다만 요청된 지연 증상과 연결 386의 관계, 지연 발생 시간대가 제공되지 않아 이 대기가 사용자가 느낀 지연을 설명하는지는 확인되지 않았습니다.

마지막 조회의 빈 결과는 해당 시점의 반환 결과를 설명합니다. 이 결과가 앞선 잠금 대기의 원인이나 지연 해소를 입증하지는 않습니다. [call-003]

### 5. 조사 한계·조회 실패

제공된 호출 자료에는 조회 실패가 없습니다. 다음 사항은 여전히 확인되지 않았습니다.

- 두 시점 사이에 대기가 계속 이어졌는지, 같은 트랜잭션에 해당하는지
- 382가 잠금을 유지한 이유와 대기의 전체 지속 시간
- 영향을 받은 요청 수와 실제 지연의 크기
- 마지막 조회 이후의 상태와 사용자가 느낀 지연의 해소 여부
- 전체 진단이 끝났는지와 필요한 조사 범위를 충족했는지

### 6. 후속 확인 사항

아래는 담당자의 확인 항목 제안이며 실행 지시나 자동 조치가 아닙니다.

| 확인 항목 | 확인 목적 |
|---|---|
| 지연 요청의 발생 시각과 연결 정보 | 관측된 잠금 대기가 요청된 증상과 연결되는지 검토합니다. |
| 당시 382의 트랜잭션 상태와 관련 기록 | 잠금 유지 이유를 좁힙니다. |
| 지연 증상의 현재 상태와 후속 관측 | 빈 결과 이후에도 증상이 남아 있는지 확인합니다. |

### 7. 호출별 상세 근거

| 호출 ID | 도구 | 반환 결과 |
|---|---|---|
| call-001 | mysql_get_lock_waits | 성공: waiting_connection_id=386, blocking_connection_id=382 |
| call-002 | mysql_get_lock_waits | 성공: waiting_connection_id=386, blocking_connection_id=382 |
| call-003 | mysql_get_lock_waits | 성공: rows=[] |

마지막 빈 행 목록을 전체 MySQL 정상 판정으로 변환하지 않습니다. 자료에 없는 지속 시간·영향 범위·원인·조치를 추가하지 않습니다.

>

> 마지막 조회에서는 대기 행이 반환되지 않았습니다. [call-003] 지연과의 관련성과 증상 해소 여부는 확인되지 않았습니다.

> **상세 조회:** Run <실제 run_id>

## 사례 B: 앞선 조회 성공 후 마지막 조회가 실패한 경우

### 1. 진단 요약

앞선 두 조회에서 연결 386이 연결 382의 잠금 해제를 기다리는 행이 확인됐습니다. 마지막 조회는 제한 시간 내 결과를 얻지 못해, 이후에도 대기가 남아 있었는지는 확인할 수 없습니다.

잠금 대기가 MySQL 지연과 관련됐을 가능성이 있습니다. 현재 자료로 원인을 확정하거나 상태가 회복됐다고 판단할 수는 없습니다.

### 2. 조사 대상·범위

- 요청된 증상: “MySQL이 느린 것 같아”
- 검토 자료: 2026-09-18 잠금 대기 조회 기록 3건
- 결과를 확보한 시점: 10:00, 10:01 UTC
- 결과를 확보하지 못한 조회: call-003, 가상 실패 기록 시각 10:02 UTC
- 포함되지 않은 정보: 실제 지연 측정값, 지연 요청과 연결 번호의 대응, 트랜잭션 상태, 전체 조사 종료·완료 정보

### 3. 확인된 사실

| 기록 시각(UTC) | 확인된 사실 | 호출 근거 |
|---|---|---|
| 10:00:00 | 연결 386이 382의 잠금 해제를 기다리는 행이 반환됐습니다. | call-001 |
| 10:01:00 | 같은 연결 번호 조합의 대기 행이 반환됐습니다. | call-002 |

마지막 조회의 시간 초과는 조회 과정의 실패 기록이며, MySQL 상태를 관측한 결과와 구분합니다. [call-003]

### 4. 원인 가설과 근거

가능성: 관측된 잠금 대기가 MySQL 지연에 영향을 주었을 수 있습니다.

이 가설의 근거는 성공한 두 조회입니다. [call-001, call-002] 마지막 조회의 실패는 잠금 대기와 지연의 인과관계를 뒷받침하는 근거로 추가하지 않습니다.

지연 요청과 연결 번호의 대응이 없어, 관측된 대기가 요청된 증상의 원인인지는 확인되지 않았습니다.

### 5. 조사 한계·조회 실패

| 구분 | 내용 | 판단에 미치는 영향 |
|---|---|---|
| 조회 실패 | call-003에서 제한 시간 내 결과를 얻지 못했습니다. | 이후 대기의 존재·부재를 확인할 수 없습니다. |
| 원인 판단 한계 | 382의 잠금 유지 이유와 지연 요청 정보가 없습니다. | 지연 원인을 확정할 수 없습니다. |
| 시간·영향 범위 한계 | 연속 관측과 요청별 영향 자료가 없습니다. | 지속 시간과 영향 규모를 산정할 수 없습니다. |
| 조사 완료 정보 부재 | 전체 종료·완료 표식이 없습니다. | 조사 전체의 완료 여부를 판단할 수 없습니다. |

조회 실패 자체를 데이터베이스 장애나 과부하의 증거로 단정하지 않습니다. 성공한 두 조회의 관측 사실도 실패 때문에 삭제하거나 무효화하지 않습니다.

### 6. 후속 확인 사항

| 확인 항목 | 확인 목적 |
|---|---|
| 지연 요청의 발생 시각과 연결 정보 | 성공한 조회의 잠금 대기와 증상을 연결할 수 있는지 검토합니다. |
| 당시 382의 트랜잭션 상태와 관련 기록 | 잠금 유지 이유를 좁힙니다. |
| 실패한 조회의 수집 경로 상태와 이후 관측 확보 가능 여부 | 조회 공백을 확인하고 대기의 현재 상태를 판단할 자료를 확보합니다. |

확인 항목은 담당자 검토 제안입니다. 자동 재시도, 추가 도구 호출 또는 연결 종료를 지시하지 않습니다.

### 7. 호출별 상세 근거

| 호출 ID | 도구 | 확보한 결과 또는 안전한 실패 설명 |
|---|---|---|
| call-001 | mysql_get_lock_waits | 성공: waiting_connection_id=386, blocking_connection_id=382 |
| call-002 | mysql_get_lock_waits | 성공: waiting_connection_id=386, blocking_connection_id=382 |
| call-003 | mysql_get_lock_waits | 제한 시간 내 결과를 얻지 못함. 결과 행 없음이 아니라 결과 미확보. |

실패 설명은 예시 문구다. 실제 오류 객체·enum·생산자 종료 상태의 확정안이 아니다.

> 마지막 조회는 시간 초과로 결과를 얻지 못했습니다. [call-003] 대기가 계속되는지와 지연의 원인은 확인되지 않았습니다.

>
> **조사 범위:** 결과 확보 2건·조회 실패 1건 · 전체 조사 완료 여부 미확인
>
> **상세 조회:** Run <실제 run_id>

## 두 사례의 표현 비교

| 항목 | 사례 A | 사례 B |
|---|---|---|
| 기존 성공 근거 | call-001·002의 관측을 보존 | call-001·002의 관측을 보존 |
| 마지막 조회 | 대기 행이 반환되지 않음 | 시간 초과로 결과 미확보 |
| 말할 수 있는 내용 | 마지막 조회의 반환 행이 비어 있음 | 마지막 조회에서 상태를 확인하지 못함 |
| 원인 판단 | 지연 관련성은 가설 | 지연 관련성은 가설 |
| 해소 판단 | 지연 증상 해소 여부 미확인 | 대기의 후속 상태와 증상 해소 여부 미확인 |
| 후속 확인의 차이 | 지연 증상과 후속 관측 확인 | 위 확인에 더해 실패한 조회의 공백 확인 |
| Discord에 남길 한계 | 빈 결과가 증상 해소를 입증하지 않음 | 마지막 조회 실패로 현재 상태를 알 수 없음 |

호출 수가 늘어도 인과관계를 입증하는 자료가 늘어난 것은 아닐 수 있다. 두 사례 모두 잠금 대기 자체의 관측과 원인 판단에 필요한 증상 연결 자료를 구분한다.

이번 비교로 제안하는 표현 원칙:

1. 요약에 핵심 발견, 마지막 조회 결과와 주요 판단 한계를 함께 둔다.
2. 관측 사실은 호출 ID와 연결하고, 가설은 이를 뒷받침하는 성공 근거를 명시한다.
3. 실패한 호출은 실패 범위와 판단 영향으로 설명한다.
4. 후속 확인은 미확인 항목과 목적을 연결한다.
5. 상세 근거가 생략돼도 Discord에 중요한 실패와 한계를 남긴다.

이 원칙과 문구는 이번 검토안이며, 추가 사용자 합의나 정본 계약 개정을 대신하지 않는다.

선택지는 기존 필드 안에서 수용 가능한 표현만 제공하거나, 범위·한계·근거 연결을 검증 가능한 구조로 보존하도록 계약을 개정하는 것이다. 전자는 변경이 작지만 상세함을 제한하며, 후자는 구조화된 표시와 추적이 쉬워지지만 스키마·조립·저장·소비자 검증을 함께 바꿔야 한다. 이번 문서는 어느 쪽도 구현 지시로 승격하지 않는다.

## 검토 기준과 이번 확인 범위

문구 검토 기준은 다음과 같다.

- 두 사례 각각 합의한 7개 구획 포함
- 본문의 관측·가설 근거 ID가 해당 사례의 호출 목록에 모두 존재
- 빈 결과와 조회 실패의 표현 혼동 0건
- 연속 대기 시간, 전체 정상, 원인 확정, 회복 완료에 대한 근거 없는 단정 0건
- Discord에서도 각 사례의 핵심 발견과 중요한 한계 보존
- 생산자 실패·종료 계약 또는 모델 출력 범위의 확정·변경 지시 0건

이는 템플릿 검토 기준이며 실행한 제품 테스트 결과가 아니다. 공통 PRD·제품 파일 수정, 제공자 호출, 실제 진단, 저장·전달 검증은 이 문서 작성에 포함되지 않는다.
